# 離線紀錄與打卡排障

看到「已暫存」或 `OFFLINE SAVED` 時，紀錄**尚未等於後端已入庫**。先恢復連線、核對裝置核准與時間，再確認管理頁有對應紀錄；切勿直接刪除待補送資料。

## 桌面端待補送

1. 確認讀卡端連到 `http://192.168.100.23:16688`，後台的裝置狀態為「已核准」且未暫停。
2. 從桌面端程序的工作目錄找 `data/offline_punches.json`。程式啟動且裝置連線正常時、連線恢復時，以及暫存後有成功打卡時會立即嘗試補送；若仍有待送事件，也會約每 5 分鐘重試。僅補送與目前 UUID 相同的事件；不要搬到另一台電腦或改動 UUID。桌面端日誌位於 `%LOCALAPPDATA%\CVTAClockIn\logs\`。
3. 恢復連線後先核對 JSON 中待送筆數是否下降；若尚未補送，再等待下一次週期，再到管理頁查同一員工及時間的紀錄。401／403 表示驗證或核准問題，不是離線成功；查裝置狀態與憑證，不要反覆刷卡製造更多紀錄。

## ESP32 待補送

1. 以序列監控器或 BLE 輸入 `status`、`queue`，確認 Wi-Fi、NTP、核准狀態及待送筆數。`TIME UNSYNC` 時先恢復時間同步；`DENIED` 時查後台狀態。
2. 恢復網路後等待自動補送，用 `queue` 確認筆數下降，再到管理頁核對原本打卡時間。HTTP 401／403 會停止補送；HTTP 400／404 事件會轉入 `.bad`，用 `bad` 查看，先比對卡號與後台資料。
3. 只有確認事件已入庫或決定如何人工補登後，才依[韌體指南](https://github.com/CVTA-Engineers/CVTA-Attendance-System/blob/master/firmware/GUIDE.md)處理指定 `.bad` 事件。`QUEUE FULL/ERR` 表示該次刷卡沒有保存，須人工處理。

## 管理頁或打卡失敗

1. 管理頁打不開：依[啟停後端](server.md)檢查程序、埠、前端內嵌檔與後端日誌。
2. 管理頁可開、刷卡無紀錄：先查讀卡端 UUID 是否已核准、是否暫停，再查卡片是否已綁定及裝置時間。未識別卡號會被後端拒絕，不能視為已入庫。
3. 後端恢復後，把待補送事件與管理頁紀錄逐筆核對。若請求已入庫但回應遺失，重送可能產生重複紀錄；遇到相同卡號與時間，先核對再人工處理。

**完成標準：**待送佇列與管理頁紀錄能對上；未入庫、重複或 `.bad` 事件各有明確處置紀錄。

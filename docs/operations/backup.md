# 人工備份與還原資料庫

目前沒有自動備份。後端**工作目錄**下的 `data/punch_hot.db` 是熱資料庫；`data/archives/punch_<年份>.db` 是可能存在的年度歸檔庫。年度歸檔函式目前未見自動排程，因此歸檔目錄可能為空。熱庫含帳號與裝置憑證，備份檔須限制存取。

熱庫現行 schema 為第 3 版，包含短期加卡命令、一次性憑證與加卡結果。升級前備份第 1 或第 2 版熱庫，並在重新啟動後確認遷移成功；備份檔同樣須限制存取。

## 備份前

1. 依[啟停後端](server.md#第一次確認啟動位置)找出真正的工作目錄，記錄熱庫與現有歸檔檔案。不要只根據 exe 位置猜測資料路徑。
2. 選擇影響較小的時段，通知現場暫停打卡；記錄各讀卡端待補送事件。這些事件不在後端資料庫備份內。
3. 決定受限制的備份位置並準備日期標記。備份頻率、保留期間及執行人目前尚未訂定。

## 執行備份

1. 依[啟停後端](server.md#停止與重新啟動)停止後端，確認 `api_server_app.exe` 已結束。不要在程序仍寫入 SQLite 時直接複製 DB。
2. 將 `data/punch_hot.db` 複製到備份位置；若 `data/archives/` 內有 `.db`，一併複製並保留其相對目錄及檔名。不要把桌面端離線 JSON 或 ESP32 佇列當成後端備份。
3. 比對來源與備份的檔案清單、大小，記下備份日期、來源工作目錄及保存位置。重新啟動後端，確認管理頁可登入、近期紀錄仍在，再通知現場恢復刷卡。

## 還原備份

1. 確認要還原的備份日期，先辨識該日期之後新增的打卡、帳號及裝置資料。還原舊熱庫會覆蓋這些變更；先決定如何核對及補登差額，並保留各讀卡端待補送事件。
2. 停止後端，將目前熱庫與歸檔庫另存為一批「還原前」副本。核對工作目錄後，才將同一批備份的 `punch_hot.db` 與既有歸檔庫放回原路徑。
3. 重新啟動後端，驗證管理頁登入、近期紀錄、裝置核准狀態及需要的年度紀錄。再依[離線紀錄與排障](offline.md)確認讀卡端補送，核對未補回的差額。

**完成標準：**備份有明確日期與檔案清單；還原演練能讀到預期紀錄，且備份後新增資料的處置已記錄。不要在沒有原始檔副本時覆寫現有資料庫。
